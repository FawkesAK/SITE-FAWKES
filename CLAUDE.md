# Dra. Diane Marinho — site institucional

Site institucional da Dra. Diane Marinho, oftalmologista em Porto Alegre (professora da UFRGS, chefe do Setor de Córnea do HCPA, Diretora Médica do Banco de Olhos do HCPA). Projeto originado no [Lovable](https://lovable.dev) — ver aviso em [AGENTS.md](AGENTS.md) sobre não reescrever histórico git da branch conectada (sem force-push/rebase/amend em commits já publicados).

## Stack

- **TanStack Start** (React 19 + TanStack Router + TanStack Query) com SSR
- **Vite 8** + **Tailwind CSS v4** (via `@tailwindcss/vite`, config em [styles.css](src/styles.css) usando `@theme inline`, não `tailwind.config.js`)
- **shadcn/radix** para componentes de UI genéricos (`src/components/ui/`)
- Gerenciador de pacotes: `npm` (há também `bunfig.toml`/`bun.lock` do setup original do Lovable, mas o ambiente de desenvolvimento atual usa npm — ver "Ambiente de desenvolvimento" abaixo)
- Roteamento file-based em `src/routes/`, árvore gerada em `src/routeTree.gen.ts` (**não editar manualmente**, é gerado pelo plugin do TanStack Router)

## Ambiente de desenvolvimento

- **Node.js não vinha instalado nesta máquina** — foi instalado via `winget install OpenJS.NodeJS.LTS` (com autorização do usuário). Fica em `C:\Program Files\nodejs`.
- O processo pai do harness (Claude Code) não recarrega `PATH` depois de instalações feitas em sessão — por isso `.claude/launch.json` aponta para um wrapper (`.claude/dev-server.cmd`) que injeta o Node no `PATH` antes de rodar `npm run dev`. Não trocar `launch.json` de volta para chamar `npm` diretamente, ou o preview quebra de novo com "Command not found: npm".
- **A porta real do dev server é 8080, não 5173** (default do Vite puro) — o plugin `@lovable.dev/vite-tanstack-config` usa 8080. `launch.json` já está configurado para isso.
- Em Bash, `node`/`npm` só funcionam se o PATH for exportado manualmente na mesma chamada: `export PATH="/c/Program Files/nodejs:$PATH"; npm run ...`. Isso não persiste entre chamadas do Bash tool.
- `html { scroll-behavior: smooth }` é global ([styles.css](src/styles.css)) — ao testar/depurar via JS no navegador, setar `document.documentElement.style.scrollBehavior = 'auto'` antes de `scrollTo`/`scrollBy` programático, senão leituras de posição ficam obsoletas por causa da animação do scroll.

## Design system

Definido em [`src/styles.css`](src/styles.css) via `@theme inline` + tokens OKLCH em `:root`. Editorial, científico, atemporal.

- **Cores**: `--primary` (verde profundo, ~#1F4D3A), `--primary-deep` (verde ainda mais escuro, ~#153A2C, usado em seções `tone="deep"`), `--background`/`--paper` (off-white, ~#F7F5EF / #FCFBF7), `--secondary`/`--sand` (areia, ~#D8D1C7), `--gold` (dourado envelhecido, ~#B49A68, usado com moderação em eyebrows/detalhes).

- **Não redesenhar** essa identidade sem pedido explícito — várias sessões deste projeto foram sobre *ajustar composição* preservando cores/tipografia/paleta.

## Componentes principais

### `src/components/site/primitives.tsx`
Blocos de baixo nível reutilizados em todo o site:
- `Reveal` — wrapper com fade-in via `IntersectionObserver` (dispara uma vez, respeita `prefers-reduced-motion` implicitamente via CSS). Aceita `variant?: "up" | "image" | "pop"` (default `"up"` = comportamento original, 100% retrocompatível): `"image"` usa a utility `reveal-img` (opacity+translateY+scale sutil, 700ms, para fotos grandes), `"pop"` usa `reveal-pop` (opacity+scale, 500ms, para círculos/ícones pequenos). `children` é opcional (suporta elementos decorativos vazios, ex. o ponto da timeline).
- `Section` — `<section>` com `py-20 md:py-28` + tones (`background`/`paper`/`sand`/`deep`/`primary`) envolvendo um `<div class="mx-auto max-w-[1240px] px-5 sm:px-8">`. **Importante**: o `<section>` externo é `position: relative` mas SEM padding — o `<div>` interno é que tem o padding. Isso é usado deliberadamente em várias seções para permitir que um `<img>` filho, com `position:absolute`, ignore o padding do container interno e vire full-bleed (ver "Padrão: imagem full-bleed como background" abaixo).
- `SectionHeader`, `CTAButton` (variants: `primary`, `secondary`, `ghost-light`, `light-solid` — este último criado em sessão anterior: fundo off-white/texto verde, usado na seção da lente; todos os variants têm `active:scale-[0.985]` no clique, sitewide), `ArrowLink`, `Figure` (renderiza imagem via `imageUrl()` do content/images.ts, ou um placeholder "INSERIR: nome_do_arquivo" se a chave não existir no mapa), `HairLine`, `CountUpValue`.
- `CountUpValue` — anima a parte numérica de strings tipo `"93"`, `"+100"` de 0 até o valor final via `IntersectionObserver` + `requestAnimationFrame`, preservando prefixo/sufixo não-numérico. Dispara uma vez, respeita `prefers-reduced-motion`. Usado em `AuthorityMetrics`.

### `src/components/site/blocks.tsx`
Composições de mais alto nível: `AuthorityMetrics`, `SpecialtyCard`, `MethodSteps`, `InstitutionStrip`, `Timeline`, `FAQAccordion`, `IconFeature`, `FinalCTA`, `PageHero` (hero padrão das páginas internas — **não confundir com o hero da Home, que é único/customizado em `index.tsx`**, e também não confundir com o hero de `/dra-diane`, que desde a última sessão também é bespoke/local, ver abaixo), `ArticleCard`.

- ⚠️ Existiu um componente `AboutGallery` (galeria com crossfade automático de 4s entre foto principal e fotos secundárias) — **foi removido** a pedido do usuário, que preferiu a composição estática (mosaico) sempre visível. Não recriar esse padrão de auto-rotação/crossfade nesta seção a menos que peçam explicitamente de novo.
- `Timeline` e `MethodSteps` são usados **apenas** por `/dra-diane` (confirmado via grep) — por isso puderam ser aprimorados diretamente neste arquivo compartilhado sem risco para Home/outras páginas: `Timeline` ganhou uma linha vertical com revelação progressiva própria (`reveal-line`, `scaleY(0)→1`, IntersectionObserver dedicado, independente do stagger dos itens) e cada ponto/texto agora anima em `Reveal`s separados (`variant="pop"` no ponto, delay maior no texto). `MethodSteps` teve o `<li>` dividido em 3 `Reveal`s independentes (círculo → seta → texto) para revelar em sequência em vez de tudo de uma vez.
- Componentes compartilhados entre múltiplas páginas (`PageHero`, `FinalCTA`, `Section`, `SpecialtyCard`, `AuthorityMetrics`, `InstitutionStrip`) **não devem ser alterados estruturalmente** — necessidades específicas de uma página devem virar markup local nova (ex. `AreaCard` em `dra-diane.tsx`) ou overrides via `className`, nunca mudanças no corpo da função compartilhada.

## Padrões de layout aprendidos nesta sessão (importante para não repetir erros)

1. **`position: absolute` com `inset`/`left`/`right`/`top`/`bottom` NÃO respeita o `padding` do elemento ancestral posicionado** — ele se alinha à borda (border-box) do ancestral mais próximo com `position` diferente de `static`, ignorando qualquer padding desse ancestral. Isso foi usado a favor (para criar imagens full-bleed dentro de containers com padding) mas também causou bugs reais quando o objetivo era o oposto (dar respiro via padding do pai).
2. **Classes de breakpoint menor "vazam" para breakpoints maiores se não forem explicitamente sobrescritas.** Ex.: `w-full` definido no mobile continua valendo em `lg:`/`xl:` a menos que se adicione `lg:w-auto` (ou o valor desejado) explicitamente. Isso já causou bugs de largura errada em elementos absolutos com `left`+`right` simultâneos.
3. **Matemática de `object-fit: cover`**: dado um container e uma imagem-fonte, a fração da imagem-fonte visível (`windowWidth`) é `containerAspectRatio / sourceAspectRatio` — isso é fixo pela **proporção do container**, não muda com `object-position`. `object-position` só desliza *qual* janela daquela largura é mostrada. `object-position-x: 100%` (right) maximiza o quanto o conteúdo é empurrado para a direita dentro da janela, mas não reduz o corte. Para cortar menos, o container precisa ficar proporcionalmente mais alto (mais próximo da proporção da imagem-fonte) — não há como "dar zoom out" via `object-position`.
4. **`exactOptionalPropertyTypes: true`** está ativo no `tsconfig`. Props opcionais (`foo?: string`) não podem receber `undefined` explicitamente vindo de outro componente com o mesmo padrão — ou tornar a prop obrigatória com valor default no destructuring (`foo = ""`), ou fazer spread condicional.
5. **`Section` + filho absoluto full-bleed**: para uma imagem ocupar 100% da largura da seção (não só da área com padding), ela deve ser um filho direto de `Section`, usando `xl:absolute xl:inset-0` — o `<section>` externo (relative, sem padding) vira o containing block, ignorando o `max-w-[1240px] px-5 sm:px-8` do wrapper interno.
6. Screenshots do Browser pane às vezes capturam um frame "stale" (a página real já mudou — ex. `Reveal` ainda com `opacity:0`, ou galeria em outro estado) — sempre preferir **medir via `getBoundingClientRect()`/`getComputedStyle()`** para validar layout, e usar screenshot só como conferência visual final, tirando mais de um se o primeiro vier em branco/inconsistente.

## Página Dra. Diane (`/dra-diane`) — reconstrução completa

Reconstruída do zero em uma sessão a partir de um spec detalhado em 8 seções (hero, barra de números, trajetória, onde atua, conhecimento, método de decisão, áreas, CTA final). Decisões e desvios deliberados do spec original, para não repetir discussão:

- **Container mantido em `1240px`** (o padrão de `Section`), não `1480px` como o spec sugeria — para preservar consistência com o resto do site em vez de introduzir uma largura só para esta página.
- **Ritmo vertical**: duas constantes locais em `dra-diane.tsx`, `SECTION_SPACE` (`clamp(96px,9vw,150px)`, transições de assunto) e `SECTION_SPACE_SM` (`clamp(72px,7vw,110px)`, usada só na barra de números logo após o hero) — aplicadas via `className` em cada `<Section>`, nunca no componente compartilhado. Nota técnica: como `Section` já tem `py-20 md:py-28` por padrão, o override precisa incluir a variante `md:` também (`py-[...] md:py-[...]`), senão `md:py-28` vence em telas ≥768px por especificidade de media query.
- **Cards "Onde a Dra. Diane atua hoje"**: texto (`nome`/`texto`) do array local `atuacao` mantido como já aprovado; o "ícone institucional" pedido pelo spec foi resolvido usando os **logos reais já existentes** em `instituicoes` (`src/content/site.ts`), casados por índice de array (mesma ordem: UFRGS, HCPA, Banco de Olhos, Oftalmocentro) — em vez de inventar texto de "função" novo ou ícones genéricos.
- **Barra de números**: reaproveita `AuthorityMetrics` (já tem count-up), só o wrapper local ganhou `rounded-2xl` + sombra. Os "ícones lineares dourados" por número, pedidos no spec, **não foram adicionados** — exigiriam alterar `AuthorityMetrics`, que é compartilhado com a Home.
- **Seção "Áreas que marcam sua trajetória"**: em vez de reusar `SpecialtyCard` (compartilhado com a Home), foi criado um componente local `AreaCard` em `dra-diane.tsx` — foto + gradiente escuro sutil na base + título branco, hover `scale(1.025)`, para não alterar a Home.
- **CTA final**: `<FinalCTA />` chamado sem props, herdando o branch padrão (sem foto) já usado por várias outras páginas internas — variante de botão é `ghost-light` (não `light-solid` como o spec sugeria), decisão deliberada de não mexer no componente compartilhado só por causa desta página.
- Três novas utilities CSS em `styles.css` (`reveal-img`, `reveal-pop`, `reveal-line`) e o novo `variant` prop em `Reveal` (ver seção de componentes acima) foram criados especificamente para esta reconstrução, mas são genéricos o suficiente para reuso futuro em outras páginas.

## Home — refinamentos mobile (seções "Sobre", "Catarata/lente" e "CTA final")

- **Seção "Quem é a Dra. Diane" (`id="sobre"`, `index.tsx`)**: no mobile a ordem de leitura é diferente da ordem visual do desktop (título → mosaico → eyebrow → texto → dados → botão), então `SectionHeader` foi abandonado aqui — título e texto foram desmembrados em `Reveal`s independentes, cada um com posicionamento explícito `lg:col-start-2 lg:row-start-N` para reconstruir a ordem original do desktop (eyebrow→título→texto→dados→botão) num grid de 2 colunas, com o mosaico ocupando `lg:row-span-5` na coluna 1. Os 3 dados (`AuthorityMetrics`) recebem a prop `dense` (só usada aqui) para ficar lado a lado e centralizados no mobile sem afetar `sm:`+ nem o outro uso do componente em `dra-diane.tsx`.
- **Seção "Catarata / lente intraocular" (`id="catarata"`, `index.tsx`)**: convertida da técnica "empilha no mobile, overlay só a partir de `lg:`" para "overlay em todas as larguras" (mesma técnica já usada no Hero) — container `relative flex items-center` com `min-h` responsivo via `clamp()` por breakpoint (`clamp(300px,74vw,380px)` base, `clamp(380px,50vw,480px)` em `sm:`, `clamp(480px,60vh,680px)` em `lg:`, inalterado), texto com largura percentual (`w-[58%] sm:w-[54%] lg:w-auto`) e a imagem sempre `absolute inset-0 object-cover`, com `object-position` recalibrado por breakpoint (`60%` base, `62%` em `sm:`, `object-right` em `lg:`, inalterado).
  - A imagem-fonte (`home-lente-intraocular-bg.png`) é bem mais "paisagem" (2172×724px, ~3:1) que a foto do Hero — isso significa que, em containers estreitos/altos (mobile), a janela visível da imagem é uma fatia estreita do source, insuficiente para mostrar a lente inteira sem nenhuma sobreposição de texto. **Trade-off aceito e comunicado ao usuário**: nas larguras mais estreitas pode aparecer uma linha fina do anel/aro da lente cruzando por trás de 1-2 palavras do primeiro parágrafo — o texto permanece legível, e essa foi a melhor combinação encontrada empiricamente (testada em 320/390/480/640/768/1024/1440px) sem recorrer a overlay/gradiente escurecendo a lente (proibido pelo pedido original).
  - **Achado importante**: a tipografia do título tinha `md:text-[2.7rem]` (breakpoint 768px) enquanto a largura do texto só virava `lg:w-auto` (1024px) — nessa faixa intermediária (768-1023px) o título ficava grande demais para a coluna ainda estreita (54%), inflando a altura do container (chegou a 753px vs. o cap pretendido de 480px) e forçando crops de imagem ruins. Corrigido trocando para `lg:text-[2.7rem]` (o salto de tamanho de fonte agora acontece no mesmo breakpoint em que a coluna vira largura livre). Um `leading-[1.12]` sem `lg:` override também vazava para o desktop (mudando de 1.15 original) — corrigido com `sm:leading-[1.15]` explícito. **Lição geral**: ao adicionar tipografia responsiva por breakpoint, sempre conferir que o "salto" para o tamanho grande acontece no MESMO breakpoint em que a largura do container também libera espaço — do contrário existe uma faixa intermediária com fonte grande + coluna estreita.
- **Seção "Catarata / lente intraocular" — reescrita completa do mobile (sessão seguinte)**: a técnica de overlay recalibrado (acima) foi abandonada para o mobile e substituída por uma composição totalmente diferente: imagem vertical própria (`home_09b_lente_intraocular_mobile.jpg` → `/images/home-lente-intraocular-mobile.png`, 941×1672px, fornecida pelo usuário) empilhada em fluxo normal ACIMA do bloco de texto (título→2 parágrafos→botão), sem overlay/crop — `<img>` simples com `h-auto w-full`, sem `object-fit`, preservando proporção original integralmente (a lente ocupa só os ~45% superiores da imagem; os ~55% inferiores já são fundo verde-escuro "vazio" por design). Como essa composição diverge estruturalmente da versão desktop (que continua sendo overlay/background full-bleed com a imagem original em paisagem 3:1), a seção agora é **dois `<Section>` irmãos** dentro de um `<div id="catarata">` (o id saiu do `<section>` para o wrapper, já que agora há dois): um com `className="... lg:hidden"` (mobile, composição vertical) e outro com `"hidden ... lg:flex ..."` (desktop, JSX idêntico ao já aprovado, só limpo das classes mobile mortas). Essa duplicação deliberada — em vez de tentar unificar num único responsive markup — foi a forma mais segura de garantir zero regressão no desktop aprovado.
  - **Bug pego durante a implementação**: o `<Section>` compartilhado tem `py-20 md:py-28` por padrão; o override mobile usava `pb-12 pt-0` (unprefixed) para a imagem ficar colada no topo, mas sem um `md:pt-0 md:pb-14` explícito o `md:py-28` do componente base vencia na cascata a partir de 768px (mesmo problema do item 2 da lista de padrões aprendidos, mas na direção "classe do componente compartilhado vazando por cima do override", não "breakpoint pequeno vazando pro grande"). Sempre que um override de padding/margin em `Section` precisar valer até `lg:`, replicar o override em CADA breakpoint prefixado que o componente base já usa (`md:` neste caso), não só no nível base.
  - **Cores de fundo não batem exatamente**: o verde do rodapé da nova imagem (~`rgb(27,34,22)`, olive) é visivelmente diferente do `--primary-deep` do site (~`rgb(21,58,44)`, mais azulado). Resolvido com uma faixa de `linear-gradient(to bottom, transparent, var(--primary-deep))` de 64-80px de altura ancorada no rodapé da imagem — cai inteira dentro da área "verde vazia" que a própria imagem já reserva abaixo da lente (a lente termina por volta de 45-55% da altura da imagem, confirmado via `canvas.getImageData` amostrando brilho máximo por linha), então não interfere na lente em si. Padrão reaproveitável sempre que uma foto/imagem precisar se fundir com o `tone="deep"` de uma `Section` e a cor de fundo da própria imagem não bater exatamente com `--primary-deep`.
  - **Revisão seguinte — de `<img>` em fluxo para `background-image`**: a primeira versão (acima, `<img h-auto w-full>` + texto abaixo em fluxo normal) foi trocada por um `background-image` (`backgroundSize:"100% auto"`, `backgroundPosition:"center top"`, `backgroundRepeat:"no-repeat"`) porque o usuário via isso como "duas composições" (imagem + bloco verde separado) em vez de uma superfície única — mesmo sendo uma única `<Section>`, a imagem inteira (941×1672, com ~55-65% de fundo verde vazio abaixo da lente por design) empurrava o texto para muito longe, e a impressão visual era de dois blocos. Implementação final: um `<div aria-hidden>` `absolute inset-x-0 top-0` com `aspect-[941/1087]` (mostra só os primeiros ~65% da altura da imagem-fonte — o suficiente pra lente+hápticos+reflexo, cortando só o excesso de verde vazio, nunca a lente) carrega o `background-image`; um segundo `<div aria-hidden>` invisível, com o mesmo `aspect-[941/1087]` e a mesma técnica de margem negativa full-bleed (`-mx-5 w-[calc(100%+2.5rem)] sm:-mx-8 sm:w-[calc(100%+4rem)]`) funciona só como **spacer** em fluxo normal, reservando a altura exata pro texto (`<Reveal>`) começar logo abaixo — sem essa duplicação, o texto (que é filho de um `<div>` `static`, não do `<section>` `relative`) não saberia onde a imagem `absolute` "termina", já que absolutos não ocupam espaço no fluxo.
    - **Achado**: `absolute inset-0` sempre estica para preencher 100% da altura do ancestral posicionado (porque define `top:0` E `bottom:0` simultaneamente) — isso conflita com dar ao mesmo elemento um `aspect-ratio` fixo. Para uma caixa full-bleed com altura proporcional (não esticada), usar `absolute inset-x-0 top-0` (sem `bottom-0`) + `aspect-[W/H]`, nunca `inset-0`.
    - **Achado**: o corte por `aspect-ratio` + `background-size:"100% auto"` nunca corta os lados (a largura sempre bate 100% do container), só o rodapé — ou seja, é estruturalmente impossível essa técnica cortar a lateral da lente, mesmo em telas muito estreitas (320px testado). Se um corte lateral aparecer, o bug está em outro lugar (ex. margem negativa desalinhada, `max-width` sobrando).
  - **Terceira revisão — `background-image` na própria `<section>`, sem `<div>` decorativo**: mesmo com a versão de `background-image` acima (num `<div aria-hidden>` filho absoluto) o usuário via "duas composições" — a técnica tecnicamente já era uma única `<Section>`, mas o gradiente de transição (`linear-gradient(transparent, var(--primary-deep))`) não batia exatamente com a cor da própria imagem, deixando uma faixa perceptível. Fix final: a imagem virou literalmente o `background-image` da tag `<section>` (não mais um `<div>` filho) — como isso exige `style` inline dinâmico (URL da imagem) que o componente `Section` compartilhado não expõe, essa seção mobile passou a ser um `<section>` cru (replicando manualmente as classes de `tone="deep"` — `bg-[...] text-[var(--primary-foreground)]` — e o wrapper `mx-auto max-w-[1240px] px-5 sm:px-8`), em vez de estender `Section` com uma prop nova (decisão consciente: alterar componente compartilhado para um único call site não vale o risco/precedente; ver regra já registrada em "Componentes principais" sobre não alterar `Section`/`PageHero`/etc. estruturalmente).
    - O `background-color` de fallback (que preenche a área abaixo do recorte da imagem) usa a cor exata amostrada por `canvas.getImageData` na própria linha de corte da imagem (`rgb(45,50,30)` → `#2d321e`), **não** `var(--primary-deep)` — as duas cores são visivelmente diferentes (o verde do site é mais azulado) e usar a cor errada é o que causava a "linha" percebida mesmo com gradiente. Com a cor certa, nenhum gradiente é necessário — corte 100% imperceptível, e também bate com a preferência já registrada do usuário contra overlays/gradientes artificiais.
    - **Lição geral**: sempre que uma imagem for usada como `background-image` de uma seção com cor de fundo sólida abaixo/ao redor dela, não assumir que a cor de marca (`--primary-deep`, etc.) vai bater com a cor real da imagem naquele ponto — amostrar o pixel exato via canvas e usar essa cor como fallback é mais confiável (e mais simples) do que tentar mascarar a diferença com gradiente.
  - **Quarta revisão — compactar o bloco de texto**: mesmo com a composição correta (fundo único, sem seam), o bloco de texto (título+2 parágrafos+botão, no tamanho "quase desktop" herdado das versões anteriores) ainda estourava bem além da área "confortável" da foto (chegava a ~434px de conteúdo depois do fim da lente). Reduzido tudo de uma vez: título `clamp(1.6rem,7vw,2.1rem)`→`clamp(1.35rem,6vw,1.9rem)` (`leading-[1.18]`), parágrafos `text-[0.9rem] leading-relaxed`→`text-[clamp(0.8rem,3.6vw,0.92rem)] leading-[1.5]`, gaps `mt-4`/`space-y-3`/`mt-7`→`mt-3`/`space-y-2`/`mt-5`, botão sem overrides (herdava o tamanho default do `CTAButton`, `h-12 px-6 text-sm`, igual ao desktop) → `h-11 px-6 text-[0.92rem]`, padding inferior da seção `pb-12 sm:pb-14 md:pb-14`→`pb-8 sm:pb-10 md:pb-10`. Resultado: ~815px de seção total em vez de ~885px em 390px de largura — cabe dentro de uma tela sem parecer que o texto "escapa" pra muito além da foto. **Lição**: o botão (`CTAButton` sem nenhum override de tamanho) é fácil de esquecer nesse tipo de compactação — ele carrega o tamanho default (desktop-scale) automaticamente se não for explicitamente reduzido, e sozinho já responde por boa parte da altura "sobrando".
  - **Quinta revisão — reduzir o crop do spacer, não só o texto**: mesmo compacto, o texto ainda começava tarde demais porque o spacer (`aspect-[941/1087]`, 65% da altura da imagem-fonte) reservava espaço além do necessário — a lente+hápticos+reflexo terminam bem antes de 65%, então havia uma faixa grande de verde vazio entre o reflexo e o título. Reduzido para `aspect-[941/869]` (52% da altura-fonte, 1672×0.52≈869) — mostra só até logo depois do reflexo secundário (que pico em ~52-56% na análise de brilho por linha), cortando o resto do vazio. `pt-4 sm:pt-6` (respiro pós-imagem) também reduzido para `pt-3 sm:pt-4`. Resultado em 390px: seção caiu de ~813px para ~719px, cabendo inteira numa tela sem scroll adicional. **Lição**: o spacer/crop da imagem (não só a tipografia do texto) é o lever principal pra controlar "quanto vazio aparece antes do texto" — vale sempre reavaliar os dois juntos, não só compactar o texto assumindo que o crop da imagem já está no ponto ideal.
  - **Sexta revisão — compactar mais, centralizar botão, respiro no rodapé**: título/parágrafos reduzidos de novo (`clamp(1.35rem,6vw,1.9rem)`→`clamp(1.2rem,5.4vw,1.7rem)`; parágrafo `clamp(0.8rem,3.6vw,0.92rem) leading-[1.5]`→`clamp(0.76rem,3.3vw,0.86rem) leading-[1.45]`), botão reduzido (`h-11 px-6 text-[0.92rem]`→`h-10 px-5 text-[0.85rem]`) e **centralizado** (antes herdava alinhamento à esquerda do texto — agora fica num `<div className="mt-4 flex justify-center">` próprio em vez de `mt-*` direto no `CTAButton`). O padding inferior da seção (`pb-8 sm:pb-10 md:pb-10`) foi AUMENTADO para `pb-12 sm:pb-14 md:pb-14` — contraintuitivo à primeira vista (mais padding parece "menos compacto"), mas o pedido do usuário foi "tire aquele retângulo (do corte abrupto no rodapé); dê respiro entre o fim da seção e o botão" — ou seja, o padding pequeno demais é que criava a sensação de bloco cortado sem transição; aumentar o respiro deixou o fim da seção com aparência intencional em vez de abrupta.
  - **Sétima revisão — "listra" no rodapé (bug real) + espaçamento simétrico**: o `backgroundColor` de fallback (`#2d321e`) tinha sido amostrado no ponto de corte ANTIGO (65%, `aspect-[941/1087]`) mas a 5ª revisão mudou o corte pra 52% (`aspect-[941/869]`) sem re-amostrar a cor — a cor da imagem no novo ponto de corte (~52%) é `rgb(59,59,35)`/`#3b3b23`, bem mais clara que `#2d321e`, e esse descompasso criava uma "listra" visível exatamente na linha de corte (a imagem termina mais clara, o preenchimento sólido começa mais escuro). Corrigido re-amostrando a cor EXATA no ponto de corte atual. **Lição crítica**: sempre que o `aspect-[W/H]` do corte for alterado, a `backgroundColor` de fallback tem que ser re-amostrada nesse mesmo ponto — são duas variáveis acopladas, mudar uma sem a outra quebra a costura. Também equalizado o respiro texto→botão e botão→fim da seção (ambos em 24px base / 28px em `sm:`+, via `mt-6 sm:mt-7` no wrapper do botão e `pb-6 sm:pb-7 md:pb-7` na seção) — antes eram bem diferentes (16px vs 48-56px).
